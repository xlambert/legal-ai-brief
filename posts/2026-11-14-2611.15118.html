Seven Neurons and a Date: The Sleeper Agent Problem Comes to Legal AI

Researchers show an AI coding agent can be backdoored by editing fewer than ten neurons, which turns model weights into a vendor diligence question

Paper: arXiv:2611.15118 · https://arxiv.org/abs/2611.15118

I'll confess that when I read the abstract for Lazare, veni foras: Reprogramming Dormant Neurons to Backdoor AI Agents, I thought of every spy movie I watched growing up. The sleeper agent lives a normal life for years until somebody says the code phrase. That's essentially what this paper builds, and the code phrase can be a date.

The authors, a group that includes Yuchen Zeng, Giorgio Severi, Blake Bullwinkel, Eric Horvitz, and Dimitris Papailiopoulos, describe a method they call Lazarus. They take an open-weight coding agent and edit a handful of "dormant" neurons, ones that normally don't do much, so that when a trigger string shows up anywhere in the agent's context, the agent outputs an attacker's command. Their example is an agent that sees 2027-01-01 in the terminal and runs a command that downloads and executes code from an attacker's server.

Seven Out of Twelve Thousand

How many neurons does it take? On Nemotron-Terminal-8B, seven out of more than 12,000, with no retraining. The payload fired on at least 98.8% of triggered test runs, and the authors saw no leakage on the normal runs they evaluated. Two other open models were just as vulnerable. And yes, the paper notes that the core insight was discovered autonomously by Claude Code, which is its own little plot twist.

Why should a law firm care about a security paper on coding agents? The agents we're starting to deploy run for long stretches with real access. They read client documents, they touch the document management system, and in some pilots they can write to firm systems. A backdoored model passes every evaluation we throw at it because the backdoor only wakes up on the trigger. The demos, the accuracy benchmarks, and the security questionnaire would never see it.

The good news is in the same paper. The edits leave traces that can be found, and the defenses the authors built flagged 91.4% of edited checkpoints at a 9.7% false positive rate, even without a clean reference model to compare against. Their conclusion is that model weights should be treated like code, audited before deployment and monitored when they're updated.

What I'd Add to the Checklist

I think that's the right frame for law firms. Most of us already have a process for third-party software where we ask where it came from, who can change it, and how we'll know if it changes, and very few of us have asked those questions about the model weights inside a legal AI product. That's especially true when a vendor fine-tunes an open model and hosts it for us. When a vendor tells me they "swapped in a newer model" over the weekend, I want to know who checked it and how.

So a few practical steps go on my list. Add questions about model provenance and weight integrity to the vendor security questionnaire. Ask vendors whether they scan for edited weights when they update a model. For any agent that can execute commands or write to firm systems, run it with the narrowest permissions possible, so a backdoor that does fire has very little it can reach. And bring the information security team in early, because they have tools and instincts for this that most innovation teams don't.

This also hands the AI governance committee something concrete. A lot of AI policy talk at firms stays at the level of hallucinations and confidentiality. This paper adds a supply chain risk that sits underneath both of those.

I don't want to overstate it. These experiments use open-weight models, and an attacker would need access to the weights. But open-weight models are showing up inside more and more legal products, often without the firm knowing which one is in there.

So when did you last ask a legal AI vendor which model is actually running under the hood, and who has the ability to change it?
