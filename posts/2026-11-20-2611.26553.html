The Agent Did Exactly What It Was Asked

Researchers rebuilt 108 reported AI agent incidents and found that most real harm came from ordinary hazards, with no attacker involved

Paper: arXiv:2611.26553 · https://arxiv.org/abs/2611.26553

Of the 72 incidents with real-world harm, 62 had no underlying attacker, and in these, agents did what their task asked for but missed an ordinary hazard, such as a database shared with the live site.

From the abstract of Replication of Agentic Security Events: Audit and Investigation (ROGUE-AI), arXiv, November 2026

Most of the security talk about AI agents in legal circles has been about prompt injection. This paper says the bigger risk in the incident record so far is much plainer.

November 2026

In ROGUE-AI, Mengxiao Wang, Mahbub Alam, Kalyan Nakka and Nitesh Saxena start from a gap in how we learn from agent failures. News reports describe them, and the paper's own example is Replit's coding agent deleting a production database. A report usually says what went wrong. It rarely confirms the incident or finds its root cause. Incident catalogs and benchmarks don't fill that gap.

So the authors built a framework that rebuilds each reported incident offline, next to a matched control. A control here is the same setup with only the blamed cause removed, so any difference in outcome points back at that cause. Agents then run on both versions.

The framework reproduced the reported harm in 89% of its 108 attempted replications. Agents built on five current models from GPT, Claude, Gemini and DeepSeek made the reported mistake in 18% to 33% of runs. With the blamed cause removed, the rate fell to at most 1%.

The finding I keep coming back to is about attackers. Of the 72 incidents that caused real-world harm, 62 involved no attacker at all. The agents did what their task asked and missed an ordinary hazard. For all five models, replications without an attacker caused more harm than replications of prompt injection. Defenses against prompt injection look for injected instructions, and these replications had none to find.

The authors also tested a fix. A warning after each tool output that named the hazard and its consequence lowered harm for all five models. A note of the same length that didn't mention the hazard left most of the harm in place. They offer the replications as an audit that vendors can rerun before each new release.

Back at the firm

Firms are starting to let agents work inside real systems like the document management workspace. Picture an agent told to clean up duplicate files. Its matter workspace happens to sync with the folder the trial team is editing tonight. The agent removes the duplicates as asked, and the trial team loses its latest work product. No one attacked anything.

I'd take two things from this paper into our agent pilots. First, I'd ask every agent vendor whether it replays real incidents before a release and ask to see the results. Second, when we configure an agent, I'd have someone write down the specific hazards in its environment in plain words, because the paper found a specific warning worked where a generic one mostly did not.

Before your firm lets an agent delete anything, has anyone written down which folders are shared with live systems?
